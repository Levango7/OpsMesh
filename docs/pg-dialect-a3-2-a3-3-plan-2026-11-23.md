## 0. 结论

1. A3-1 只解决了「PG 能启动」，**没有解决「PG 能承载业务写入」**。仓库 CHANGELOG 自己写了：
   > 「本批只到『结构就位 + 方言接口』，**PG 下的业务写入路径尚不可用**」。
2. 真正的阻断不是 95 这个数字，而是三类**具体能力缺口**：通用 Upsert、LIMIT-OFFSET 分页、DDL 自增翻译（A3-2/A3-3）。
3. 48 处 UPSERT 里 **45 处是同构的**（`col=VALUES(col)`，含常量/`NOW()` 覆盖），可以机械翻译；**3 处是特例**（条件表达式、计数器自增、lifecycle_jobs 隐式更新时间），需要专用方言适配。因此这是一个「接口先行 + 批量机械迁移 + 3 个特例」的工程，不是 48 次独立开发。
4. 已批准交付方式为 **1 个 PR**，内部按域分批提交；国产 DB 驱动（达梦/金仓）放最后另立，openGauss 可借 pgx 协议先接。

## 1. 现状取证

### 1.1 已落地的地基（A3-1）

`internal/store/sqlstore/dialect.go`（325 行）当前 `Dialect` 接口 15 个方法：

```
DriverName  PrepareDSN  ConvertPlaceholders  InsertIgnore  SchemaMigrationsDDL
SetLockWaitTimeoutStmt  AcquireMigrationLock  ReleaseMigrationLock
CurrentDatabaseQuery  MigrationFS  HasLegacyFixups  IsIdempotentDDLError
IsLockTimeoutError  DDLTargetExistsQuery  IdentifierQuote
```

注释自认的能力边界（L17-19）：

> 「只接本批有消费者的方法；无消费者的能力（LIMIT-OFFSET 分页、通用 Upsert、DDL 自增翻译）不入口，列 A3-2/A3-3，避免死键。」

依赖侧：`go.mod` 只有 `go-sql-driver/mysql v1.10.0` + `jackc/pgx/v5 v5.13.0`，**无达梦/金仓驱动**。

### 1.2 48 处真实 UPSERT 的分布

| 文件 | 真实处数 | 文件 | 真实处数 |
|---|---:|---|---:|
| `sql_devices.go` | 6 | `sql_billing.go` | 3 |
| `sql.go` | 3 | `sql_m2.go` | 2 |
| `sql_automation.go` | 2 | `sql_pipeline.go` | 2 |
| `sql_tasks.go` | 2 | `sql_templates.go` | 2 |
| 其余 25 个文件 | 各 1 | | |

按形态统计：

| 形态 | 处数 | PG 等价写法 |
|---|---:|---|
| `col=VALUES(col)` 简单覆盖（含常量与 `NOW()`） | 45 | `ON CONFLICT (<唯一键>) DO UPDATE SET col=EXCLUDED.col` |
| `version=version+1` 计数器自增 | 1（`sql_abac_policy.go:80`） | `version = <表名>.version + 1`（PG 需用表名限定，不能直接裸列） |
| 条件表达式 `IF(expires_at < ? OR holder=VALUES(holder), ...)` | 1（`sql.go:1028`，leader_lease） | `CASE WHEN ... THEN ... ELSE ... END` + `EXCLUDED` |
| 隐式 `updated_at`（MySQL 列定义 `ON UPDATE`） | 1（`sql.go:1095`，lifecycle_jobs） | PG 特例在 `DO UPDATE SET` 中显式补 `updated_at=now()` |
| `INSERT IGNORE` | 0 处遗留 | 已由 `dialect.InsertIgnore()` 抽象为 `ON CONFLICT DO NOTHING` |

> 注：A3-3 实际范围是 UPSERT 写路径方言化；`Page` 与 `AutoIncrementColumn` 仍列后续能力，不在本批扩展 `Dialect`。最终设计见 `docs/superpowers/specs/2026-11-24-a3-3-upsert-dialect-design.md`。

### 1.3 三个能力缺口的具体含义

| 缺口 | 现状 | 需要补什么 |
|---|---|---|
| **通用 Upsert** | 48 处手写 MySQL SQL 文本，方言层无入口 | `Dialect.Upsert(table, cols, values, conflict, updateCols) string`；MySQL 出 `ON DUPLICATE KEY UPDATE col=VALUES(col)`，PG 出 `ON CONFLICT (conflict) DO UPDATE SET col=EXCLUDED.col` |
| **LIMIT-OFFSET 分页** | 各 store 方法内手写 `LIMIT ?, ?`，无方言入口 | `Dialect.Page(suffix, offset, limit)`；PG 出 `LIMIT $n OFFSET $m`（占位符编号需与 `ConvertPlaceholders` 协同） |
| **DDL 自增翻译** | MySQL 迁移用 `AUTO_INCREMENT`，PG 迁移另写一份 001 | `Dialect.AutoIncrementColumn(type)`；MySQL `BIGINT AUTO_INCREMENT`，PG `BIGINT GENERATED BY DEFAULT AS IDENTITY` |

**额外风险点**：`ON CONFLICT (col) DO UPDATE` 要求目标列有**唯一约束**。当前 48 处 UPSERT 的 MySQL 语义依赖任意唯一键（可能是主键，也可能是二级唯一索引）。改造前必须逐表核对 PG 迁移里是否建了对应的唯一约束——`migrations/pg/001_initial.sql` 是另写的一份，不能假设与 MySQL 侧一致。这是本次改造最容易翻车的地方。

## 2. 已批准拆分（1 个 PR，内部分批提交）

### 批次 1：方言接口与守卫地基

- `Dialect` 新增 `Upsert(table, cols, values, conflict, updateCols) string`，MySQL/PG 两套实现。
- PG 直接生成 `$n` 与双引号标识符；参数仍由调用方按原顺序传入。
- 补纯逻辑单测、AST 调用点守卫、UPSERT 目标唯一约束 parity。
- `Page` 与 `AutoIncrementColumn` 不在本批新增。
- 验收：单测与静态守卫绿；新增裸 SQL、错误 conflict target、漏唯一约束三种窄变异均能报红。

### 批次 2：45 处通用 UPSERT 批量迁移

按域分批，建议顺序：

1. `sql_templates.go` / `sql_script.go` / `sql_config.go` 等纯 CRUD。
2. `sql_devices.go`（6 处）/ `sql_m2.go`（2 处）。
3. `sql_billing.go`（3 处）/ `sql_tasks.go`（2 处）/ 其余业务表。

每批必须同步补真 PG 用例（不是 sqlmock），由 `OPSMESH_TEST_PG_DSN` 门控，验证「插入 → 重复插入 → 读回正确」。`tenants` PG 冲突目标选 `id`，`cloud_resources` 选自然键 `(cloud_account_id, resource_type, resource_id)`；跨唯一键冲突在 PG 下严格报错，避免假成功。

- 验收：业务生产 Go 文件中裸 `ON DUPLICATE KEY UPDATE` 仅剩 3 处特例；全部通用调用点通过 MySQL/PG 真库 `PREPARE`。

### 批次 3：3 处特例与真库回归

- `RenewLeadership`：MySQL 从左到右赋值归约为旧行条件，PG 用 `CASE WHEN ... THEN EXCLUDED... ELSE ... END`；补并发抢占不双主用例。
- `UpsertABACPolicyRecord`：PG `version=abac_policies.version+1`；补并发版本不丢更新用例。
- `CreateLifecycleJob`：MySQL 保留隐式更新时间；PG 特例显式补 `updated_at=now()`，不改已应用的 PG 001 迁移。
- PG `PrepareDSN` 强制 `TimeZone=UTC`，补真库 `SHOW TimeZone` 断言。
- 验收：业务裸 UPSERT 为 0；MySQL 真库行为回归绿、本机 PG15 真库 UPSERT/PREPARE/并发用例绿。

### 后续另立：国产数据库驱动接入

- openGauss：走 pgx 协议，先验证方言兼容；达梦/金仓：引入专用驱动，新增一套 `Dialect` 实现。
- 每种 DB 至少一套真库 CRUD + 幂等 + 迁移用例，并产出兼容性报告；不在 A3-3 范围。

## 3. 验收口径（防止「看起来完成」）

项目历史上多次出现「报告写完成、代码查无实据」（见审计报告 §4 的产品文档口径问题）。本改造的验收必须同时满足：

1. **静态**：业务生产 Go 文件中裸 `ON DUPLICATE KEY UPDATE` / `ON CONFLICT` 为 0；只有三个特例适配允许出现原始方言 SQL。
2. **动态**：`OPSMESH_TEST_PG_DSN` 指向真 PG15 时，UPSERT/PREPARE/幂等/并发用例真实执行（不是 skip）；无 DSN 时明确 skip。PR #160 最终合入 `postgres:15` service，CI 通过 `OPSMESH_TEST_PG_DSN` 真跑 PG 门控用例；该接线已于 2026-11-26 追认。
3. **约束**：从 AST 收集全部 UPSERT 目标，核对 MySQL 唯一索引集合 ⊆ PG 唯一约束集合；解析结果为空必须报红。
4. **不回退**：MySQL 侧 48 处语义、参数顺序和写后结果等价，用 MySQL 真库跑同一组行为用例；不承诺 SQL 文本逐字节相同。
5. **门禁射程**：新增裸 SQL、错误 conflict target、漏 PG 唯一约束三种窄变异均须报红，还原后转绿。
