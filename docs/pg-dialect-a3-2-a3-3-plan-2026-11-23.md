## 0. 结论

1. A3-1 只解决了「PG 能启动」，**没有解决「PG 能承载业务写入」**。仓库 CHANGELOG 自己写了：
   > 「本批只到『结构就位 + 方言接口』，**PG 下的业务写入路径尚不可用**」。
2. 真正的阻断不是 95 这个数字，而是三类**具体能力缺口**：通用 Upsert、LIMIT-OFFSET 分页、DDL 自增翻译（A3-2/A3-3）。
3. 48 处 UPSERT 里 **46 处是同构的**（`col=VALUES(col)`），可以机械翻译；**2 处是特例**（条件表达式、计数器自增），需要人工设计。因此这是一个「接口先行 + 批量机械迁移 + 2 个特例」的工程，不是 48 次独立开发。
4. 建议拆成 **4 个 PR / 约 3–4 周**，每个 PR 独立可验收；国产 DB 驱动（达梦/金仓）放最后，openGauss 可借 pgx 协议先接。

## 1. 现状取证

### 1.1 已落地的地基（A3-1）

`internal/store/sqlstore/dialect.go`（325 行）当前 `Dialect` 接口 15 个方法：

```
DriverName  PrepareDSN  ConvertPlaceholders  InsertIgnore  SchemaMigrationsDDL
SetLockWaitTimeoutStmt  AcquireMigrationLock  ReleaseMigrationLock
CurrentDatabaseQuery  MigrationFS  HasLegacyFixups  IsIdempotentDDLError
IsLockTimeoutError  DDLTargetExistsQuery  IdentifierQuote
```

注释自认的能力边界（L17-19）：

> 「只接本批有消费者的方法；无消费者的能力（LIMIT-OFFSET 分页、通用 Upsert、DDL 自增翻译）不入口，列 A3-2/A3-3，避免死键。」

依赖侧：`go.mod` 只有 `go-sql-driver/mysql v1.10.0` + `jackc/pgx/v5 v5.13.0`，**无达梦/金仓驱动**。

### 1.2 48 处真实 UPSERT 的分布

| 文件 | 真实处数 | 文件 | 真实处数 |
|---|---:|---|---:|
| `sql_devices.go` | 6 | `sql_billing.go` | 3 |
| `sql.go` | 3 | `sql_m2.go` | 2 |
| `sql_automation.go` | 2 | `sql_pipeline.go` | 2 |
| `sql_tasks.go` | 2 | `sql_templates.go` | 2 |
| 其余 25 个文件 | 各 1 | | |

按形态统计：

| 形态 | 处数 | PG 等价写法 |
|---|---:|---|
| `col=VALUES(col)` 简单覆盖 | ~46 | `ON CONFLICT (<唯一键>) DO UPDATE SET col=EXCLUDED.col` |
| `version=version+1` 计数器自增 | 1（`sql_abac_policy.go:80`） | `version = <表名>.version + 1`（PG 需用表名限定，不能直接裸列） |
| 条件表达式 `IF(expires_at < ? OR holder=VALUES(holder), ...)` | 1（`sql.go:1028`，leader_lease） | `CASE WHEN ... THEN ... ELSE ... END` + `EXCLUDED` |
| `INSERT IGNORE` | 0 处遗留 | 已由 `dialect.InsertIgnore()` 抽象为 `ON CONFLICT DO NOTHING` |

> 注：`VALUES(col)` 在 MySQL 8.0.20+ 也已进入弃用期，迁移到 `EXCLUDED` 对 MySQL 侧同样是 modernization，不是纯 PG 妥协。

### 1.3 三个能力缺口的具体含义

| 缺口 | 现状 | 需要补什么 |
|---|---|---|
| **通用 Upsert** | 48 处手写 MySQL SQL 文本，方言层无入口 | `Dialect.Upsert(table, cols, uniqueCols, updateCols) (sql, args)`；MySQL 出 `ON DUPLICATE KEY UPDATE col=VALUES(col)`，PG 出 `ON CONFLICT (uniqueCols) DO UPDATE SET col=EXCLUDED.col` |
| **LIMIT-OFFSET 分页** | 各 store 方法内手写 `LIMIT ?, ?`，无方言入口 | `Dialect.Page(suffix, offset, limit)`；PG 出 `LIMIT $n OFFSET $m`（占位符编号需与 `ConvertPlaceholders` 协同） |
| **DDL 自增翻译** | MySQL 迁移用 `AUTO_INCREMENT`，PG 迁移另写一份 001 | `Dialect.AutoIncrementColumn(type)`；MySQL `BIGINT AUTO_INCREMENT`，PG `BIGINT GENERATED BY DEFAULT AS IDENTITY` |

**额外风险点**：`ON CONFLICT (col) DO UPDATE` 要求目标列有**唯一约束**。当前 48 处 UPSERT 的 MySQL 语义依赖任意唯一键（可能是主键，也可能是二级唯一索引）。改造前必须逐表核对 PG 迁移里是否建了对应的唯一约束——`migrations/pg/001_initial.sql` 是另写的一份，不能假设与 MySQL 侧一致。这是本次改造最容易翻车的地方。

## 2. 建议拆分（4 个 PR，约 3–4 周）

### PR-A：方言接口补齐（1–2 天）

- `Dialect` 新增 `Upsert` / `Page` / `AutoIncrementColumn` 三个方法，MySQL/PG 两套实现。
- `dialect_test.go` 补 parity 测试：**同一输入两边输出各自的合法 SQL**，并断言关键 token（`VALUES(` vs `EXCLUDED.`）。
- `Upsert` 的 `uniqueCols` 必填——杜绝「靠MySQL猜唯一键」的隐式行为，PG 侧没有唯一约束就直接返回错误让调用方补迁移。
- 验收：`go test ./internal/store/sqlstore/...` 全绿；无真实 PG 依赖（纯字符串测试）。

### PR-B：46 处同构 UPSERT 批量迁移（3–5 天，建议按域再切 2–3 个提交）

迁移顺序建议按「风险从低到高」：

1. `sql_templates.go` / `sql_script.go` / `sql_config.go` 等纯 CRUD（10 处）——验证机械翻译成立。
2. `sql_devices.go`（6 处）/ `sql_m2.go`（2 处）——带状态字段与租户字段，验证 `tenant_id` 不被 upsert 改写。
3. `sql_billing.go`（3 处）/ `sql_tasks.go`（2 处）/ 其余——业务关键表。

每批必须同时补 **真 PG 用例**（不是 sqlmock）：用 `TEST_PG_DSN` 门控，验证「插入 → 重复插入 → 读回值正确」的幂等闭环。

- 验收：生产 Go 文件中 `ON DUPLICATE KEY` 命中从 48 降到 2（只剩两个特例）。

### PR-C：2 个特例 + DDL 自增（2–3 天）

- `sql.go:1028` `RenewLeadership`：`IF(expires_at < ? OR holder=VALUES(holder), VALUES(holder), holder)` → `CASE WHEN ... THEN EXCLUDED.holder ELSE leader_lease.holder END`。这是**选主原子性**路径，必须有并发用例（多实例抢占不双主）。
- `sql_abac_policy.go:80`：`version=version+1` → `version=abac_policies.version+1`，并验证 PG 下版本并发递增语义与 MySQL 一致。
- 迁移文件里 `AUTO_INCREMENT` 统一走 `Dialect.AutoIncrementColumn`，核对 PG 001 的唯一约束覆盖全部 48 处 UPSERT 目标表。
- 验收：真 PG 实例上跑通 `go test -tags pg`（若引入 tag）或既有 DSN 门控用例。

### PR-D：国产数据库驱动接入（1–2 周，单独决策）

- openGauss：走 pgx 协议，先验证方言兼容；达梦/金仓：引入专用驱动，新增一套 `Dialect` 实现。
- 这一步同时卡住「信创准入」与「自身 store」，但依赖 PR-A/B/C 完成才有意义。
- 验收：每种 DB 至少一套真库 CRUD + 幂等 + 迁移用例；产出可交付的兼容性报告（版本、驱动版本、已知差异）。

## 3. 验收口径（防止「看起来完成」）

项目历史上多次出现「报告写完成、代码查无实据」（见审计报告 §4 的产品文档口径问题）。本改造的验收必须同时满足：

1. **静态**：`git grep -n 'ON DUPLICATE KEY' -- 'internal/store/sqlstore/*.go'` 只剩注释（真实 SQL 为 0）。
2. **动态**：`TEST_PG_DSN` 指向真 PG 实例时，幂等/分页/自增三组用例真实执行（不是 skip）；无 DSN 时明确 skip 且在 CI 日志中可见。
3. **约束**：PG 迁移对 48 处 UPSERT 的目标表逐一有唯一约束；写一个自检测试比对「MySQL 侧唯一索引集合 ⊆ PG 侧唯一约束集合」。
4. **不回退**：MySQL 侧 48 处行为逐字节等价（`dialect.go` 设计约束第 1 条），用 MySQL 真库跑同一组用例对拍。
