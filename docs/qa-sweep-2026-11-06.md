## §1 五维度审计规程

“不能转化为生产力”在本仓库的具体形态只有四类，全部以**用户可感知**为准绳：
**①点了没用**（404/405/403/静默失败）、**②看到的和真实的不一样**（假数据、口径漂移、跨租户串数据）、
**③该有的没有**（能力残缺/未接线/缺反馈）、**④要重复劳动**（同一件事每个页面各写一遍、口径不统一）。

### D5 方法论自身的严谨性（防"审计出假债"）

1. **只在当前 HEAD 取证**：每条发现的证据必须是"我现在就能复算的"（文件行、命令输出、测试红绿），不引任何过期报告的数字。
2. **静态匹配只是线索**：落账前必须回到运行时语义（路由真身、权限点真身、handler 真身）核对一次。
3. **反向证伪优先**：凡"没有调用方/没有消费"类结论，先排除三种已知假阴性——运行时拼接 URL、动态 import、目录字面量（11-04 教训：`git cherry` 判"无独有内容"被证伪）。
4. **报告与门禁双轨**：一次性报告进 `docs/`；可机检的判据必须固化成 `internal/gates/*_test.go` 或 `scripts/*.py`（否则下一轮又漂移）。
5. **修复必须钉住**：每修一条，至少一个测试会在"改回旧行为"时判红（窄变异反证 ≥1 例）。
6. **假阳性同样记账**：误报要在台账里写明"为什么不是缺陷"，避免下一轮重复花时间（沿用 35 条 Mimosa findings 分诊做法）。

一次全量比对可同时产出 D1-3 / D2-3 / D3-1 / D3-4 / D3-5 五类判据的台账：

```
后端路由注册 ──┐
              ├─→ 匹配 ─→ 每条：METHOD PATH / handler / 权限点 / 前端 api 函数 / 消费视图 / 视图内是否挂门
前端 api 端点 ─┘
```

配套脚本（本轮落地，`scripts/` 下）：
- `scripts/qa-matrix.py`：产出矩阵 TSV + 异常行（幽灵调用=前端有后端无；死面=后端有前端无；写面无门=前端写调用 × 视图无 hasPerm × 后端有对应 write 权限点）。
- 既有 `scripts/authz-route-audit.py`（RBAC 覆盖）、`internal/gates/ops_route_ratchet_gate_test.go`（棘轮）继续作为 D1-3 的双口径，不重复造。
