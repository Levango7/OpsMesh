# ADR-2026-11-15 — 高并发与规模化四项决策

状态：**已决策（Accepted）**　决策人：kilo（lead）　日期：2026-11-15

> 背景：链路体检（批次20-26）后剩余 4 项涉及策略/架构。本文给出明确取舍、触发阈值与实施顺序，
> 避免"边做边议"。后续实现必须对齐本文；偏离需追加新 ADR。

## ADR-1 限流策略：双层限流 + 分维度失败语义 + XFF 可信 CIDR

### 决策
1. **两层限流，各自独立**：
   - L1 按客户端 IP：`200 req/s`，桶数上限 50000（现状保留）。
   - L2 按租户：`1000 req/s`（可由 `--tenant-rate-limit` 覆盖），桶数上限 = 租户数 × 1（有界）。
2. **失败语义分维度**：
   - L1 桶满（新 IP 未跟踪）→ **保持 fail-open**。理由：现有 `limiter_test` 已固化该取舍——
     攻击方早已持有桶并受限流，放行新 IP 不削弱在途抑制，同时避免 NAT 后正常用户被误杀。
   - L2 租户桶超限 → **fail-closed（429）**。理由：租户维度桶数天然有界（不构成内存面），
     且这是多租户公平性的唯一闸门；单租户刷量不得拖垮其他租户。
3. **XFF 信任收敛**：
   - `--trust-proxy=false`（默认）：只认 `RemoteAddr`。
   - `--trust-proxy=true` 时必须同时提供 `--trusted-proxies=<CIDR,...>`；未提供则**拒绝启动**
     （配置错误显式失败，不静默降级为"信任任意 XFF"）。
   - `clientIP()` 改为：仅当 `RemoteAddr` 落在可信 CIDR 内才解析 XFF，取最右侧非可信跳。
4. 429 响应统一带 `Retry-After: 1` 与 `X-RateLimit-Dimension: ip|tenant`。

### 实施顺序
`clientIP CIDR 校验 → L2 租户限流 → 配置项与启动校验 → 测试（含 NAT/伪造 XFF 用例）`

## ADR-2 SSE 跨副本：Redis Pub/Sub（不用 Kafka/NATS）

### 决策
1. 事件发布改为**双写**：本地订阅表（单实例路径不变）+ `PUBLISH opsmesh:sse:<tenantID>`。
2. 每实例启动时 `PSUBSCRIBE opsmesh:sse:*`，收到后仅向**本实例**的订阅者 fan-out；
   跨租户过滤仍在本地二次校验（防订阅通配泄漏）。
3. 降级：`--redis-addr` 为空 ⇒ 只走本地广播（现行为），日志 WARN 一次"SSE 仅单实例"。
4. `Last-Event-ID` 断点续传**不做**（v2 议题）：当前补偿手段是前端轮询（5s/10s）+ 重连全量刷新。
5. 慢消费者策略不变：`chan(16)` 非阻塞丢弃（保广播延迟）。

### 取舍理由
- 选 Redis 而非 NATS/Kafka：auth-svc 已依赖 Redis，运维面零新增；SSE 事件量小（状态变更），
  Pub/Sub 的"至多一次"可接受（丢失由轮询兜底）。
- 不做事件持久化：引入 Stream 会带来消费组/ACK/堆积治理成本，与"状态变更可靠送达由轮询兜底"
  的现有契约重复。

## ADR-3 分页契约：显式分页 + 全量上限

### 决策
1. **契约冻结**：
   - 带 `page` ⇒ `{data,total,page,pageSize,hasMore}`（现状）。
   - 不带 `page` ⇒ 原数组，但**硬上限 2000**；截断必须回 `X-Truncated: true` 与 `X-Total-Count`（已实现任务列表）。
2. **前端接入范围（只改长列表）**：`TasksView`、`AlertsView`、`UsersView`、`TenantsView` 四个视图改为
   服务端分页（`pageSize=20`）；其余列表天然小于 200，保持全量。
3. `devices` 例外：保持 segment map 形态（前端 `Object.entries` 契约），分页只用响应头传递元数据。
4. 默认 `pageSize=20`、上限 200 不变。

### 取舍理由
- 不做"全局强制分页"：`/devices`、CMDB 类型等小集合全量更简单，强制分页会让 80% 视图做无意义改造。
- 只对"会无限增长"的四个集合做服务端分页，收益/风险比最高。

## ADR-4 读写分离与 MQ：延迟引入，设定触发阈值

### 决策
**v1（当前，单主库）已足够**：连接池 50/10/30m + 批次26 复合索引 + 全量上限。
不引入读副本与外部 MQ——理由是本地/单机房部署无云资源（约束 `storage_no_cloud_resources`），
过早引入会让部署与故障面翻倍。

**v2 触发条件（任一满足）**：
- 任务列表/详情 P99 > 300ms 持续 15 分钟；
- `tasks` 表行数 > 500 万 或 `audit_log` > 2000 万；
- 控制面 QPS > 1000（单实例基准压测值）。

**v2 实施顺序（届时按序执行）**：
1. 只读副本：列表/详情/统计走 replica（`dbresolver` 或双 DSN），写走主库；
2. 任务分发迁移到 **Redis Stream**（不用 Kafka，沿用 ADR-2 的 Redis 依赖）：
   controlplane 写任务表 + `XADD`，worker 消费组消费；agent 拉取保留为兜底通道；
3. 审计/日志归档到冷存（已有 archive 链路），业务库只保留热窗；
4. 压测基线（k6）纳入发布门禁：P99 < 300ms、错误率 < 0.1%。

### 取舍理由
- MySQL 单主在 1000 QPS/500万行内配合索引可稳定运行；读写分离是"到阈值再做"的确定性动作，
  不是当前瓶颈。
- 选 Redis Stream 而非 Kafka：削峰量级（任务下发）远低于 Kafka 的经济规模，Redis 已在依赖内。
