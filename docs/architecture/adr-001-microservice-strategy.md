# OpsMesh 架构决策记录（ADR）

## ADR-001: 微服务拆分策略

### 状态
已接受

### 背景
OpsMesh 原为一体式架构（controlplane 136 文件 / 52K 行），随着功能增长，单体架构在构建速度、独立部署、团队并行开发方面出现瓶颈。

### 决策
采用**渐进式微服务拆分**策略，分 4 个 Phase 完成：

1. **Phase 1（地基强化）**：事件总线、指标、链路追踪、健康检查
2. **Phase 2（服务提取）**：将单体拆分为 10 个独立微服务
3. **Phase 3（AIOps 智能化）**：增加智能分析引擎
4. **Phase 4（生态扩展）**：插件市场、自助门户、Grafana 桥接

### 后果
- **正面**：独立部署、独立扩展、技术异构、团队并行
- **负面**：分布式复杂性、网络延迟、运维成本增加

## ADR-002: 服务通信协议

### 状态
已接受

### 背景
微服务间需要选择通信协议。gRPC 性能高但需要 protobuf 工具链；HTTP JSON 简单但性能较低。

### 决策
- **控制面 ↔ Agent**：gRPC + JSON codec（已有实现，无 protobuf 依赖）
- **微服务对外**：HTTP JSON API（简单、可调试、Grafana 兼容）
- **服务间**：HTTP JSON（初期简单，未来可升级为 gRPC）

### 后果
- **正面**：无 protobuf 工具链依赖、浏览器可直接调试、Grafana 原生兼容
- **负面**：序列化性能低于 protobuf、无强类型契约

## ADR-003: 数据存储策略

### 状态
已接受

### 背景
每个微服务应有独立数据存储，但初期共享 MySQL 实例可降低运维成本。

### 决策
- **初期**：所有服务共享 MySQL 实例，按 service 前缀分表
- **中期**：核心服务（device/task/alert）独立数据库
- **长期**：按服务特性选择存储（时序数据→VictoriaMetrics，日志→Loki/ES）

### 后果
- **正面**：初期运维简单、数据一致性强
- **负面**：表名耦合、未来迁移成本

## ADR-004: AIOps 算法选择

### 状态
已接受

### 背景
AIOps 引擎需要在准确性和复杂度之间平衡。深度学习准确性高但需要大量数据和 GPU。

### 决策
采用**纯 Go 实现的统计方法**：
- **异常检测**：Z-Score、EWMA、IQR（无外部依赖）
- **根因分析**：时间关联 + 指标关联 + 拓扑关联
- **告警降噪**：聚类去重 + 抖动检测 + 关联压缩
- **预测告警**：线性回归 + 趋势分析
- **智能巡检**：风险评分模型

### 后果
- **正面**：零外部依赖、启动快、资源占用低
- **负面**：准确性低于深度学习方法、需要调参

## ADR-005: 双版本策略（Lite / Professional）

### 状态
已接受

### 背景
不同规模客户需求不同。中小企业需要简单易用，大型企业需要可扩展。

### 决策
- **Lite（当前单体）**：docker-compose 单 binary，适合 ≤500 台设备
- **Professional（微服务群）**：K8s 部署，适合 10 万+ 设备
- **共享核心代码**：internal/store、internal/automation 等包共享
- **升级路径**：数据兼容，一键迁移

### 后果
- **正面**：覆盖全客户群、代码复用
- **负面**：需要维护两套部署配置
