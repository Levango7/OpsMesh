## 1. P1 CI 可信度（P0，阻断切版）

### 1.1 事实（现查，可复现）

- **当前红**：run `42321960462`（head `553e2bb`，merge PR #11）结论 `completed/failure`，唯一失败 job = `build-test`。
  - 失败段：`tick` 到 `internal/agent` 时裸 `SIGSEGV`，栈顶落在 `internal/agent/safego.go:53`（goroutine 373，`selectgo` → `safeGo.func1`）。
  - 重试判据结论为 **red（真实失败）**：日志里没有「用例跑完」的证据（既无裸 `PASS` 行也无 `ok` 结果行），因此没有把半途崩溃当 flaky 重试。
  - **不是 OOM**：同段日志 `[mem] agent_JZ MemTotal=15983MB MemAvailable=14966MB`，最大常驻 266,528 KB。
- **队列中**：run `42325117381`（head `a08c693`，merge PR #9）仍 `queued`，其结论未知。
- **历史同族**：该包曾因「agent 批次瞬时大分配」造成 build-test OOM flaky（见本线任务台账 #32），这次的形态是 SIGSEGV 而非 OOM，不能套用旧结论。
- **门禁现状**：`ci.yml` 13 个 job（build-test / integration / security / proto / frontend / e2e-real / e2e-sec / race / release-dryrun / image / image-agent / release，另有 `services` 辅助块）；build-test 是唯一 required 主闸。
- **判据风险**：把「重跑绿」当交付证据会掩盖真红——仓库已有明确规矩（flaky 先读现场、不改配置凑绿）。

### 1.2 目标 / 非目标

- **目标**：① 当前红转绿且能说出根因；② 建立「同一 SHA 复跑对照」的 flaky 分诊台账，连续 30 天每个红 run 有归因（真红 / flaky / 环境）；③ 切版前 build-test 在目标 SHA 上全绿。
- **非目标**：不重写 CI 架构；不为了绿而放宽重试判据；不把 race 之外的慢测试删掉换绿。

### 1.3 方案与取舍

| 方案 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **A. 止血** | 只在 `internal/agent` 定位 SIGSEGV（最小复现用例 + 修根因），当前红转绿 | 0.5–2 人天（取决于是否可复现） | 若与并发/第三方库相关，可能一次修不掉 |
| **B. A + 分诊台账** | A 之上，把每次 build-test 红按「真红/flaky/环境」登记，同 SHA 复跑作为对照证据 | +0.5 人天建表，之后每红 5 分钟 | 台账会暴露更多 flaky，短期观感变差 |
| **C. B + 全面加固** | 给 build-test 加隔离、并行度上限、包级超时与内存上限 | +2–4 人天 | 改 CI 判定面属禁区（`.github/workflows/` 不归本线），且可能把真红藏进重试 |

**本线选：A + B**。C 里「改 CI」需要 owner 与 workflow 归属方，且本仓明确要求「修复版本禁止跨仓照抄」；先不动。

### 1.4 验收

1. run `42321960462` 的同类失败在目标 SHA 上不再出现；修完后至少连跑 2 次（不同 SHA 或 `workflow_dispatch`）全绿。
2. 能写出一句话根因 + 一份最小复现命令（本机或 CI 均可）。
3. 台账里每个红 run 都有归因；「重跑绿」只作为归因证据，不作为结论。
4. `go test ./internal/agent/ -race -count=1` 本机复跑 3 次不崩。

### 1.5 风险与单列项

- SIGSEGV 可能是**测试间状态污染**（safeGo 的 goroutine 在用例结束后仍访问已释放状态），修错方向会掩盖更深的泄漏。
- 若根因在第三方库或 runtime，需要允许「暂时隔离该用例 + 保留 issue」，但不能删断言。
- **归属**：`internal/agent` 最近改动者不明，需板面认领，避免与并行线撞车。

## 2. P2 能力深度矩阵（P1）

### 2.1 事实（现查）

- 控制面注册路由 **610** 条：**586** 条有 RBAC 权限检查，**5** 条仅校验租户，**19** 条启发式判为匿名（多为登录/健康/公开只读）。
- **可派发路由 416 条，其中无 RBAC 的 = 0**——2026-11-04 审计的「42% 可派发路由无权限」已收口（`python scripts/authz-route-audit.py` 复算）。
- `internal/controlplane/*ops*.go` 非测试文件 **94** 个；显式 `StatusNotImplemented` 仅 **7** 处（`internal/ai/agent/handler.go:117`、`audit_query.go:283`、`deploy/handler.go:222/701/746`、`k8slifecycle/handler.go:466`、`logstore/handler.go:152`）。
- 发布说明自认：**「21 运维域是广度覆盖，深度不齐」**，多数端点形态是 shell 模板下发（`docs/release-notes.md` v0.17.0 能力降级清单）。
- 文档侧：`docs/api-reference.md` 5,389 行 / **346 个端点小节** / 51 章；相对 610 条注册路由，覆盖是「广但非穷尽」。
- 自动化侧：e2e 仅 5 个 spec（alerts / auth / devices / k8s / tasks），**107 个 `test()`/`describe()` 调用**；416 条可派发路由里绝大多数没有端到端证据。

### 2.2 目标 / 非目标

- **目标**：产出一张机器可核对的「能力—证据」表：每个运维域一行，列 `端点族 → 前置（目标机/凭据/包管理器）→ 形态（真执行/模板下发/501）→ 已验证环境 → 已知限制 → 证据（命令/结果/run id）`。
- **非目标**：不新增功能；不为凑表去改 handler；不改 release notes 的历史口径。

### 2.3 方案与取舍

| 方案 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **A. 高风险 10 域** | 先覆盖 db 备份/恢复、db 复制、中间件部署（Kafka/Redis/ActiveMQ）、网络、安全加固、K8s 集群部署、文件共享、SSH 互信、DNS/NTP | 3–5 人天（含环境） | 需要可破坏的演练机；部分域依赖软件包源 |
| **B. 21 域全量** | 一次性全表 | 8–15 人天 | 大量域在演练台无前置，表会写成「未验证」占多数 |
| **C. 只细化降级清单** | 把 v0.17.0 的 5 条扩成 30 条文字 | 0.5 人天 | 不回答「能不能跑」，只回答「我们承认不齐」 |

**本线选：A**。B 的边际信息量低；C 已有雏形，价值在 A 产出后再回写。

### 2.4 验收

1. 10 个域各至少 1 次「成功」与 1 次「可归因失败」（前置缺失/权限/网络），每次带命令、目标环境、版本 SHA。
2. 表中每行状态只能是 `已验证` / `未验证`；**没有证据不得标 ✅**（与 `capability_evidence_gate` 同一口径）。
3. 发现的真缺陷按「归属 + 优先级」入 `docs/tech-debt.md` 或板面，不在本文直接修。
4. 矩阵落 `docs/`，并挂到 README 功能矩阵的「证据」列（只加指针，不改既有 ✅ 文案）。

### 2.5 风险与单列项

- 演练环境是硬前置：本机 kind 曾压爆 VM，优先用 compose 整栈；需要 owner 确认能否复用 `e2e-real` 的 compose 口径。
- 部分域需要真实目标机（SSH、DNS、NTP、文件共享），无前置时只能标「未验证」，**不得用「代码看起来对」替代证据**。

## 3. P3 测试纵深（P1）

### 3.1 事实（现查）

- Go：非测试 **520** 文件 / **152,755** 行；测试 **421** 文件 / **5,095** 个 `Test*` 函数。
- 覆盖率门禁：整体 **≥45%**（原 50%）、store 包 **≥32%**（原 65%）；CI 注释记录真实 mysql+redis 下 store 实测 34.6%。
- 前端：**84** 个视图，视图级 spec **16** 个（约 19%）；`src` 下 spec/test 文件合计 **73** 个。
- E2E：mock 一套 + `e2e-real`（docker compose 整栈）+ `e2e-sec`（mTLS 安全契约），共 5 个 spec。
- **无压测结果**：仓库内没有任何负载测试产物；商业评估已点名「每 agent 2s 一次取消轮询 ⇒ 1000 agent ≈ 500 req/s 固定开销，应实测确认」（`docs/commercial-readiness-review-2026-09-25.md` 阶段四）。

### 3.2 目标 / 非目标

- **目标**：① 一份可复跑的压测基线与结果；② 覆盖率门槛回抬有依据（先量化差距，再抬门，不直接改数字）；③ 前端高频写视图的交互 spec 从 16 提到 ≥26（新增 10 个）。
- **非目标**：不为覆盖率写无断言测试；不用「元素存在」冒充「可见可交互」；不把 flaky 测试标 skip 凑绿。

### 3.3 方案与取舍

| 方案 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **A. 压测优先** | 固定机器/版本/并发，跑 100/500/1000 agent 的心跳、拉取、结果回写，给出 p50/p99、CPU/内存、固定轮询开销 | 3–5 人天 | 需要独立环境；本机资源可能不够 |
| **B. 前端优先** | 给 10 个高频写视图补交互 spec（含禁用态、错误可见、二次确认） | 3–4 人天 | 与前端归属方（zcode）撞车的风险，需板面认领 |
| **C. 覆盖率回抬** | 逐包统计缺口，补到 50% 再抬门 | 8–15 人天 | 容易催生低价值测试 |

**本线选：A + B-min**。C 是长期项，先把「门为什么降」写清楚（是否因新增低覆盖包稀释），再决定补哪里。

### 3.4 验收

1. 压测脚本入库（Go benchmark 或独立 harness 均可），文档写清机器、版本、并发、指标定义。
2. 结果至少包含：1000 agent 下控制面 CPU/内存、心跳与拉取的 p50/p99、单位时间固定请求数。
3. 前端新增 spec 必须断言「可见且可交互」或「错误可见」，至少 1 条负向断言；新增 spec 在 CI 与本地都跑。
4. 覆盖率：先产出「按包缺口表」，再单独出抬门 PR；抬门必须带本机与 CI 两处读数。

### 3.5 风险与单列项

- 压测数字必须标注条件（冷/热、并发、库状态）——本仓已因「冷启动标成热态」吃过一次错。
- 前端 spec 的 jsdom 陷阱：元素存在 ≠ 可见可点，必须带 `isVisible()` / 交互断言。
- 视图 spec 会碰 `web/enterprise`，若 zcode 在持，需先协调。

### 5.2 目标 / 非目标

### 5.3 方案与取舍

| 方案 | 内容 | 代价 | 风险 |

| **B. A + 报价/EULA 草案** | 需法务与业务输入 | 5–8 人天 + 法务 | 工程侧无法单方定稿 |
| **C. 全量 GTM** | 定价、渠道、案例、支持体系 | 非工程 | 不在本仓范围 |

**本线选：A**；B/C 交 owner 决策。

### 5.4 验收

1. 在一台没有本仓历史状态的机器/容器上，严格按 SOP 从零起栈，30 分钟内可登录并完成一次任务下发。

3. 许可说明与 `LICENSE` / `NOTICE` / 企业版闸门行为一致（未授权时是说明页而非企业应用）。
4. 第三方复现：至少一次由非本线成员按文档复跑并记录偏差。

### 5.5 风险与单列项

- 交付 SOP 会暴露「开箱即用」的最后一公里问题；发现即入 tech-debt，不在 SOP 里美化。
- 定价/EULA/SLA 属 owner + 法务，本线不代签、不承诺。
