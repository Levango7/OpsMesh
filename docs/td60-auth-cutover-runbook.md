# TD-60 auth 收敛运维 Runbook（分批切换执行手册）

> **适用范围**：按决策单 Q1-A（文件名册）+ Q2-A（job 搬号）+ Q3-A（允许切换即重登）执行
> 「控制面本地 auth → auth-svc」的分批收敛。前置条件与机制说明见
> `docs/td60-cutover-signal-design.md` §10.4 与 `docs/td60-domain-convergence-analysis-2026-10-11.md` §3。
> 全线可回退；**任何一步异常先回退再排查**，不带着半切状态过夜。

## 0. 前置检查（每次执行前 5 分钟）

```bash
# ① 双轨机制就绪：代理面通、名册文件在位
curl -s -o /dev/null -w '%{http_code}' http://<控制面>/api/v1/auth-svc/me   # 期望 401（端点在、需凭证）
# ② auth-svc 侧健康：管理端点可达
curl -s -o /dev/null -w '%{http_code}' http://<auth-svc>/api/v1/users        # 期望 401/403（需管理员凭证）
# ③ 名册文件路径与当前内容（控制面 30s 轮询热加载）
cat "$AUTH_CUTOVER_ROSTER_FILE"
```

**准入判据**：三条都符合才进第 1 步；任何一条不符 → 停，先修再排期。

## 1. 批次划分（提案 §11 参数）

| 批 | 范围 | 观察窗 | 备注 |
|---|---|---|---|
| **第 0 批（彩排）** | 1 个**内部/演示**租户的用户 | 2 个工作日 | 不惊动真实客户；目标=验证全流程而非切流量 |
| **第 1 批** | 1 个**低风险真实**租户（愿意配合、有直接联系人） | 2 个工作日 | 第一次真实流量验证 |
| **第 2 批起** | 每批 **≤5% 租户且 ≤3 个租户**（取小者） | 2 个工作日 | 稳定后翻倍 |
| 上限 | **25% 封顶** | — | 超过必须重新评估 |
| 最后一批 | **不要把最大/最复杂的客户留到最后一把** | — | 单独成批、单独通知 |

**保留账号永不入册**：`admin`（两侧 seed 同名，job 装载期即拒）。

## 1.1 前置条件与批次约束（2026-10-12 批次 0 演练实测）

1. **对侧 admin 必须已完成首登改密**：auth-svc 侧 admin 同样有强制改密；未完成时迁移 job 会 fail-closed 并提示
   「对侧管理员 "admin" 处于首登强制改密态：请先用该账号人工登录完成改密，再跑迁移」——先按提示人工改密一次即可。
2. **一次性口令必须与"需重新登录一次"的通知同时送达**：演练（三个模拟用户）一致证明 **OTP 是切换后唯一的自救入口**；
   界面上不存在"账号已迁移/请用一次性口令登录"的引导，全部报错文案都是给机器看的。
3. **批次划分要考虑同一出口 IP**：登录闸是同 IP 令牌桶，**实测突发 5 次**（其后每约 6 秒补 1 枚），429 文案为
   `too many requests, slow down` 且**无 Retry-After**。同办公室/同 VPN 出口的用户在同一时间窗集中登录时，
   只有前约 5 人能成功，其余被 429 挡住并很可能误判为"切换把认证搞坏了"。⇒ 同出口用户错峰分批；
   若确需集中切换，另行评估窗口内临时提高 burst（会削弱撞库防护，需拍板）。

## 2. 单批执行（五步）

### 2.1 预热（切换前 ≥3 个工作日，非本机操作）

在 auth-svc 侧为**本批全部用户**建号并审批。**门槛**：该批全部用户都能在 auth-svc 侧完成一次登录
（影子路径自测，不经控制面）——未达成不进下一步。

> **2026-10-12 更新（已透传）**：`opsmesh cutover-migrate --force-change` 建号时即置
> `mustChangePassword`（对侧入口 `3261169` + 本侧透传 `8870d69`）⇒ 一次性口令真正**只用一次**，
> 用户首次登录即被要求改密。**执行第 2.3 步时请带上 `--force-change`**——不带则该口令就是
> 长期口令（旧行为，仅当批次用户明确接受长期口令时才这样跑）。口令交接口径见 §4。

### 2.2 用户通知（切换前 1 个工作日）

告知本批用户：**切换后需重新登录一次**（Q3-A 语义：旧会话不被对侧承认）。
不专门做前端提示（Q4 建议 A/B 由产品定）。

### 2.3 切换（写名册）

```bash
# dry-run 先看计划（零副作用：不建号、不写名册）
opsmesh cutover-migrate --users alice,bob --dry-run \
  --auth-svc-url http://127.0.0.1:8100 --auth-svc-admin-password '***' \
  --store mysql --mysql-dsn '...'

# 确认无误后执行（幂等：已在对侧 active 的用户只收编、不建号）
# —— 建议带 --force-change：一次性口令只使用一次，用户首登即须改密（见 §2.1 注）
opsmesh cutover-migrate --users alice,bob \
  --auth-svc-url http://127.0.0.1:8100 --auth-svc-admin-password '***' \
  --store mysql --mysql-dsn '...' --force-change \
  --credentials-out /secure/creds-batchNN.txt
```

判据：退出码 0（全成功）；有失败 ⇒ 只重跑失败者（幂等）。

### 2.4 生效与抽验（切换后 30s 内）

控制面 30s 轮询热加载名册。抽验三条：

| 抽验 | 期望 |
|---|---|
| 本批用户经控制面 `/api/v1/auth/login` 登录 | **200**（由 auth-svc 应答） |
| 本批用户**旧本地口令**登录 | **401**（路由已切走） |
| 非本批用户登录 | **200 且走本地**（控制面路由日志无该用户的转发记录） |

### 2.5 观察窗（2 个工作日或覆盖一次登录高峰，取长）

每小时看一次；触发任一回退判据立即按 §3 回退。

## 3. 回退

**单用户/整批回退：用 `cutover-unroute`（首选；粒度=名单）**

```bash
# 先 dry-run 看计划（只读：不摘名册、不吊会话、不登录对侧）
opsmesh cutover-unroute --users alice --dry-run   --roster-file "$AUTH_CUTOVER_ROSTER_FILE" --auth-svc-url http://auth-svc:8100   --auth-svc-admin-password '***'

# 执行：一次调用完成「摘名册 + 吊销对侧会话」
opsmesh cutover-unroute --users alice,bob   --roster-file "$AUTH_CUTOVER_ROSTER_FILE" --auth-svc-url http://auth-svc:8100   --auth-svc-admin-password '***'
```

**为什么不是手改名册**（2026-10-12 演练 F2 的结论，已在 job 里收口）：名册只决定**路由**。
只摘名册能回退**登录**，但对侧已建立的会话仍被对侧认（refresh 返回 200），而 `/me` 已按名册
回本侧（401）⇒ 用户看到"刷新说还活着、一干正事就报错"的**半死态**。`cutover-unroute`
摘完名册会顺手调对侧的吊销端点（auth-svc `POST /api/v1/users/{id}/revoke-sessions`）清掉它。
**手改文件不会吊销**——所以回退请走本命令。

命令行为要点：
- **先摘名册、后吊销**：对侧不可达时名册照摘（回退已生效），失败逐条打印并可用**重跑补吊销**（幂等）；
- 会预检「该用户在本侧是否还有账号」，缺失则**告警不阻断**（摘除后他两侧都登不进，需人工处置）；
- 摘除后在名册末尾追加 `# cutover-unroute <时间> removed=N`，与迁移的来源注释一样可 diff、可审计。

**整批回退**：`--users` 给本批全部用户名。回退后旧本地口令重新生效（路由回本地）。

**硬回退**（面级）：把 compose 的 `AUTH_CUTOVER_ROSTER_FILE` 置空并重启控制面 ⇒
名册为空、全部回本地登录面。

### 3.1 回退路径的实测数字（2026-10-12 真进程冒烟，`deploy/scripts/smoke-cutover.sh` 第 10 节）

| 路径 | 实测 | 依据 |
|---|---|---|
| 软回退（清空/摘除名册，不重启） | 生效等待 **20~23s**（上限＝重载周期 30s + 一次请求） | 冒烟第 10a 节把实测秒数打进结论；周期硬编码见 `cutoverRosterLoop` |
| 硬回退（空名册 + 重启） | 旧进程退出 → 新进程就绪 **约 4~6s**；判据是「端口先释放、再重新应答」 | 冒烟第 10c 节 |
| 已签发会话在回退后 | **不搁浅**：由 auth-svc 签发的 rt 仍按归属侧转发并可继续刷新 | 冒烟第 10b 节 |

**回退前必须知道的语义边界**（同一节冒烟的副产品）：

- 软回退后，名册用户回到**本侧原口令**登录（本侧密码从未被改写），响应体形态也回到本侧（body 带 token；对侧只走 Set-Cookie）——可据此判别"是否真的回退了"。
- 回退**不回滚已完成的账号迁移**：对侧账号仍在，只是不再被路由；重切时该用户直接继续用对侧账号即可（幂等）。
- 本冒烟用 memory 后端，重启会清空账号数据，故 10c 段在新进程上重建本地账号后再验证登录；**生产（SQL 后端）重启不清号**，回退后用户直接可登——这一点两侧不同，勿照搬冒烟步骤到生产。

**回退的已知时效（2026-10-12 演练实测，待对侧补吊销接口后收紧）**：被摘除用户在对侧已建立的会话，
回退后**仍可能成功 refresh 一次**（refresh 按 rt 归属侧裁决、恒转发对侧），而 `/me` 已按名册走本侧 ⇒
出现"刷新说还活着、一干正事就 401"的半死态。前端会在一轮往返后自愈（401→refresh→重试再 401→跳登录），
**风险主要在只看 refresh 的 API 消费方**。彻底修法需对侧提供"按用户吊销会话"的管理端点（目前只有自助 logout），
详见 `docs/td60-batch0-drill-2026-10-12.md` F2。

**回退必做**：通知本批用户“需重新登录一次”；回退后 24h 内不重切该批——
重切前必须查清原因并把漏检点补进 §2.1 门槛。

## 4. 凭据交接（一次性口令）

`cutover-migrate` 输出的一口令是**一次性随机强口令**（24 位四类字符）：

- 默认打到 stderr（运维终端）——**注意终端历史与会话录屏**；
- 生产必须用 `--credentials-out <path>`（落盘 0600，建议放保密目录）。
- 交接后**立即删除该文件**；口令只经安全渠道给用户本人（禁止进工单/IM）。
- **带 `--force-change` 时**：清单头部会写「口令只使用一次，首登即要求改密」——
  交接时顺带告知用户"首次登录会跳改密页"，免得上线后误以为故障；交接口径与不带时相同。

**一个已复核的边界（peer 独立验收时提出）**：口令/路由 ID 不进指标标签
（`route` 标签来自服务端生成的十六进制 ID、`tenant` 来自已校验的令牌声明），
且渲染侧对标签值有白名单收紧（非白名单字符折叠为 `:other`，无法伪造额外标签）。
这两点由 `TestGatewayMetricLabelsNotUserControllable` 常驻守着。

## 5. 回退判据（观察窗内任一命中即停批回退）

| 判据 | 阈值 |
|---|---|
| 本批登录失败率 | > 切换前同租户基线 **+0.5 个百分点** |
| “用户不存在”/凭证无法解析类错误 | 出现**任意一次**（非密码错） |
| 本批 401/403 请求数 | > 基线 **2 倍**且绝对值 **≥10** |
| auth-svc 不可用 | 任意时长（控制面代理层会 502/503） |
| 429 计数（同 IP 突发 5） | 出现即说明有用户在某出口 IP 集中登录；**> 5 分钟内持续出现**按本批回退处理 |
| `/me` 401 的文案分布 | 大量 `user not found` = 正常（迁移后旧会话按设计失效，用户需用 OTP 重登）；`user not found` 之外的新文案才是异常面 |
