## 0. 结论

**两个都不选。原问题的前提有一半是错的。**

- **「删半边重复代码」不成立。** 我在初次评估中报的「13 对 `pkg/`↔`internal/` 近重复」经逐对核对**不成立**：7 对同名包中 6 对的导出符号**交集为零**，重名纯属命名撞车。`pkg/` 不是单体的复制品，而是微服务**唯一合法**的共享层（Go 的 `internal/` 可见性规则决定了 18 个服务模块在物理上无法 import 根模块的 `internal/`，已实测：全仓 0 处引用）。按「重复」删掉它，等于删掉微服务能编译的唯一理由。
- **「继续切流」也按现有计划走不通。** 计划所依赖的两个前提都不存在：没有路由开关，也没有影子流量比对。更严重的是，**当前出厂配置下 5 个已转发的域是坏的**（见 §2.1），这是本次核查发现的生产缺陷，优先级高于任何架构决断。

建议改为 **C 案：先接通、再裁决**，用 1 天时间把 §2.1 修掉并补上路由开关这个唯一缺失的原语，然后对每个服务做**有证据的单点裁决**。真正该删的死代码只有约 0.5k 行（§3），不是「一半」。

## 2. 三个必须先摆正的事实

### 2.1 【P0，出厂即坏】5 个转发域在默认生产栈里指错后端

`internal/controlplane/service_proxy.go:58-110` 用一张**编译期硬编码的 Go 字面量表**决定转发，地址只从环境变量读、否则回落到硬编码的 localhost 默认值（`:182-195`）。

而**全仓没有任何一个部署清单设置过 `*_SVC_URL`**（已核对 `docker-compose.prod.yml` / `.env` / `prod-proxy.yml` / `dual-track.yaml`，0 处命中）。于是 controlplane 容器内实际生效的是这些默认值：

| 域 | 默认值 | controlplane 容器内的 127.0.0.1 上有谁在听 | 实际结果 |
|---|---|---|---|
| `/api/v1/gpu` | `:8090` | 无 | 预检拨号失败 → **503** |
| `/api/v1/runbooks` | `:8082` | 无 | **503** |
| `/api/v1/incidents` | `:8082` | 无 | **503** |
| `/api/v1/autoscaler` | `:8080` | **控制面自己** | 改写成 `/api/v1/rules`（未注册）→ **404** |
| `/api/v1/portal` | `:8080` | **控制面自己** | 改写成 `/api/v1/quotas`（**已注册于 `server_lifecycle.go:233`**）→ **静默返回单体的配额数据** |

最后一格最危险：`/api/v1/portal/quotas` 不报错、不告警，返回的是另一个子系统的数据。运维看到「有数据、格式对、就是不对」，比 503 难查一个数量级。前端确实在调这些端点（`web/enterprise/src/api/{gpu,runbook,incident,autoscaler,portal}.js`），不是死代码。

**结论：GPU / Runbook / Incident / Autoscaler / Portal 五个功能域在出厂配置下不可用。** 这不是「双轨未切」的中间态，是「已接线但接错线」。

### 2.2 双轨机制只剩骨架，且计划依赖的能力从未存在

| 计划假设 | 实际 |
|---|---|
| 有路由开关 / 特性开关 | **无**。`serviceProxyRules` 是静态表，注册与匹配均无条件（`server_lifecycle.go:78-84`） |
| 有按租户 / 百分比的灰度 | **无**。全仓无 `split_clients`、无权重、无租户路由 |
| 影子流量 + 响应比对 | **无**。`cutover_response_mismatch_total` 等指标名**只存在于 `docs/td60-cutover-plan.md`，代码里零实现** |
| 控制面通过 gRPC 调服务 | **无**。只有 HTTP 反代（`service_proxy.go:244`） |
| operator 会部署微服务 | **无**。`operator/internal/controller/builders.go` 只构建 controlplane / agent / mysql / redis |

`docs/td60-cutover-plan.md` 附录 A 列的 11 个待建文件（`prometheus-cutover-alerts.yml`、`otel-collector-cutover.yaml`、`cutover-rollback.sh`、`nginx.conf.template` 等）**一个都不存在**。这份 1642 行的文档目前是一份没有实现体的设计稿。

唯一真正跑起来的双轨组件是 `services/task-svc/internal/scheduler/shadow.go` 的只读评估循环，它**只写 Prometheus gauge，不发任何流量**；且它用 `t.CreatedAt` 去重而真实触发路径用 `t.LastFiredAt`（`task-svc/cmd/task-svc/main.go:201`），两套引擎口径不一致。

### 2.3 微服务在出厂栈里「在跑，但没人调」

9 个服务在 `docker-compose.prod.yml` 里有定义（auth/device/task/alert/config/log/gpu/aio/portal），端口全部绑 `127.0.0.1`（如 `:463` 的 `127.0.0.1:8100:8100`）；`deploy/docker/proxy/nginx.conf.template:18` 只有**一个** upstream `opsmesh_controlplane`；Helm 里 16 个服务键**全部 `enabled: false`**；前端无一处引用 8100-8109。

`docker-compose.dual-track.yaml` 起了 controlplane + auth-svc + device-svc + task-svc，但其中**三个没有一个能通过代理表被访问到**：auth-svc 和 task-svc 根本没有代理规则，device-svc 跑在 8101 而代理默认指向 8081 且 compose 未设 `DEVICE_SVC_URL`。它是一个并排的 E2E 测试台，不是一套路由拓扑。

## 4. 三个方案的判定

| | A. 继续切流 | B. 删一半 | **C. 先接通再裁决** |
|---|---|---|---|
| 前提是否成立 | ✗ 依赖的开关与影子比对不存在 | ✗ 依赖「重复」判断，已被推翻 | ✓ |
| 处置 41.8k LOC 已测服务 | 保留 | **删除**，且理由错误 | 按证据逐个裁决 |
| 是否修复 §2.1 生产缺陷 | 间接 | 否 | **是，第一步** |
| 风险 | 在坏配置上继续演进，故障面扩大 | 删掉唯一能横向扩展的实现；微服务重写成本远高于维护 | 需 1 人日接入 + 逐服务评估 |
| 可逆性 | 低 | **不可逆** | 高 |

**选 C。** 关键理由有两条：

1. **B 不可逆且建立在错误前提上。** 微服务不是重复代码。删掉它们之后，18 个服务共 21k 行测试全部作废，日后要恢复只能从 git 里再翻出来，而届时的分支状态已不可考。**先做不可逆的大删除，代价远高于多做两周评估。**
2. **A 之所以现在做不得，恰恰是因为 §2.1。** 在「转发指错后端」的状态下谈切流，是在给一条接错的线路做流量规划。先把线接对，才知道哪个后端值得切过去。

### 5.1 第 1 步：接通（已实施）——含一处设计修正

1. **compose 补 `*_SVC_URL`**（`deploy/docker/docker-compose.prod.yml`）：为 `gpu-svc:8107`、
   `portal-svc:8109`、`device-svc:8101` 显式设置。`runbook`/`incident`/`autoscaler`
   三个域的微服务**不在本栈内**，故不设置——保持默认值 → 503（可见故障），
   好过指向一个不存在的服务。`docker-compose.dual-track.yaml` 同步修正
   （原 `DEVICE_SVC_URL` 缺失导致 device 域全 503），并显式停用栈内不存在的那五个域。
2. **自环硬拦截**（`service_proxy.go` `proxySelfLoopTarget` / `handleServiceProxy`）：
   后端主机为回环**且**端口与控制面自身监听端口（HTTP/gRPC/metrics）重合时，
   请求侧直接 503 并在响应体里指明该设哪个环境变量。
3. **启动自检**（`validateServiceProxyTargets`）：启动时把全部自环配置打进日志。

   > **设计修正（原方案为「启动即失败」，已改）**：控制面单体还承载鉴权、任务下发、
   > 设备纳管等全部核心流量。为了 GPU 域的转发地址写错就把整个控制面拖停，
   > 等于用五个功能的故障换全站故障——**可用性优先于严格性**。真正的兜底必须在
   > 请求侧：命中自环就 503，绝不把请求转发回自己。
   > 启动自检降级为「醒目日志」，供排障时一眼定位。

### 5.2 第 2 步：补上唯一缺失的原语（已实施）

- **路由开关 `OPSMESH_SERVICE_PROXY`**（`serviceProxy.go` `parseDisabledProxyDomains`）：
  未设置 / `on` / `all` = 全转发；`off` / `none` = 全停用；或逗号分隔的域列表。
  停用的域**不注册**代理路由，请求自然回落到单体的同名 handler——这才是真正的
  可逆回退（若单体本就没有该域实现，mux 直接 404，这比「停用后返回 503」更诚实）。
  **取值非法时整体拒绝并按「全转发」继续**：误切生产流量的代价远大于「没切」，
  绝不做「尽力而为的部分生效」。
- **路由状态端点 `GET /api/v1/admin/service-routing`**（`service_proxy_status.go`）：
  一次返回「域 → 实际后端（来自 env 还是默认值）→ 是否真的转发 → 状态
  （ok/self-loop/unreachable/disabled）→ 处置建议」。
  自环判定复用与代理同一个函数，因此端点结论与实际行为**不可能不一致**。

**第 1 幕（基线，全转发）——`GET /api/v1/admin/service-routing` 实测输出：**

|---|---|---|---|---|
| gpu | http://gpu-svc:8107 | env | ok（healthy） | 404（探测路径不在服务路由表内，**404 来自 gpu-svc 本身**，恰证转发链路通） |

其余域**不受影响**；`/api/v1/portal/quotas` 落到单体 mux → 诚实 404（单体只有 `/api/v1/quotas`，

**第 3 幕（P0 复现）**：把 `PORTAL_SVC_URL` 置空模拟「忘了配」→ portal 域判定为 **self-loop**，
启动 ERROR + 请求 503 带处置指引。出厂事故（portal 静默转回自己）的静默通道已关死。

**第 0 幕（旧镜像对照，`opsmesh/controlplane:0.9.0` + 同样错误配置）**：
`/api/v1/portal/quotas` → **HTTP 400 "Client sent an HTTP request to an HTTPS server."**
——旧代理把请求以 http 打到自己的 TLS 端口。即：**HTTPS 直连形态下旧缺陷表现为莫名其妙的 400**；
明文（反代 overlay）形态下才会表现为「静默返回单体配额数据」。两种形态都是坏的，
新代码统一为「启动告警 + 503 + 精确处置指引」。对照幕顺带证明：compose 里补的
`GPU_SVC_URL` 对旧二进制同样生效（旧镜像 + gpu 域实测 200 `[]`）。

**模拟还揪出并修复了一个新缺陷（RBAC 权限快照不回填）**：admin 首登后调
`/api/v1/admin/service-routing` 得到 `403 permission denied: diagnostics:execute`。
根因：`seedRBAC` 对 permissions 目录每次启动补种（INSERT IGNORE），但对 **roles 表
同样用 INSERT IGNORE——角色行首建后永不更新**。本库 09-24 由 0.9.0 建库，
`role-admin` 的权限快照停在 86 项、缺后加的 `diagnostics:execute/dump`，于是
**所有 `/api/v1/admin/*` 端点（loglevel/config/diagnostics/store-failures/service-routing）
对升级部署的真实管理员全部 403**。代码注释所称「requirePermission 对 admin 不受影响
（admin=全量）」只在网关注入身份路径成立（运行时取 `RolePermissions()`），用户中心
JWT 路径嵌入的是库里过期快照——两条身份路径两套真相。修复：`sql_rbac.go` 对三个
预置角色做**并集回填**（只加不减，保留客户经角色管理 API 的自定义；`mergePermissionLists`

### 5.7 代理身份头统一治理（§5.6 遗留项收口）（2026-09-29）

**遗留项 1 收口（代理域未获身份注入）**

#### ①b 转正落地复核发现的新缺陷：`occurred_at` 只在 compose 初始化 SQL 里（本次修，已加守卫）

转正把 `occurred_at`（MTTD 起点）加进了 `deploy/docker/scripts/init-mysql.sql:569`，
但**没有**加进服务自己的建表语句——而后者才是「服务自建表」部署路径（K8s / 自备 MySQL）的
唯一 schema 来源：

- `services/incident-svc/internal/store/mysql.go` 的 `initSchema` 里
  `CREATE TABLE IF NOT EXISTS incidents (...)` **不含 `occurred_at`**；
- 同一文件 `CreateIncident` 的 INSERT 与 `GetIncident` / `ListIncidents` 的 SELECT **都引用它**；
- `CREATE TABLE IF NOT EXISTS` 在既有库上是 no-op ⇒ 既有部署永远不会补列。

净效果：**在非 compose 的部署里，每次 `CreateIncident` 都因 Unknown column 失败**。
`NewMySQLStore` 的错误在 cmd 侧是 fail-fast（不退内存），所以表现为服务起不来或首次写入即失败——
两种都比「看起来正常但写不进去」好，但都不是能发布的状态。
这是「同一份 schema 有三处副本、只改了其中一处」的典型形态，而且**只在服务自建表时暴露**
（compose 里表由 `init-mysql.sql` 预建，于是缺陷被初始化脚本掩盖）。

修法（三处 + 一条守卫）：

1. `initSchema` 的 DDL 补上 `occurred_at DATETIME`；
2. 新增 `ensureIncidentColumns`：查 `information_schema.columns`，缺列时
   `ALTER TABLE incidents ADD COLUMN occurred_at ...`——MySQL 8 无 `ADD COLUMN IF NOT EXISTS`，
   故必须预检（幂等，重复启动不报 Duplicate column）；失败向上抛 → cmd 侧 fail-fast；
3. `internal/store/schema.sql`（参考 schema）同步补列，消除第三份过期副本；
4. 新增 `internal/store/schema_drift_test.go`：从源码里取出 DDL 列集合，断言所有
   `INSERT INTO incidents (...)` 与 `SELECT ... FROM incidents` 引用的列都在其中，
   并断言补列路径存在。**变异检验**：删 DDL 里的 `occurred_at` → 判红（3 条 SELECT 与 INSERT 均报缺列）；
   把迁移语句改名 → 判红（补列路径断言）。

  - 耗时参考：`internal/controlplane` 451.6s、`internal/store` 783.9s（**需 `-timeout 2400s`**，默认 600s 会误报为超时失败）、`internal/agent` 61.4s、`cmd/opsmesh` 65.4s。

  Windows 上的两个坑，CI 配置时注意：**用 `set "CGO_ENABLED=1"`，不要写 `set CGO_ENABLED=1 &&`**——后者会把值写成带尾随空格的 `"1 "`，变量非法且现象具有迷惑性（看起来像 cgo 根本不支持）。

- **开 `-race` 抓到两处竞态，均已修复（2026-09-27）。两处都不在普通测试的视野里**，`go vet`、覆盖率、代码走查全都没报。

  **① 真 bug，会崩进程（`services/workflow-svc/internal/engine`）**
  所有出口（`StartExecution` / `GetExecution` / `ListExecutions` / `GetApproval` / `ListApprovals`）都直接返回引擎持有的 `*Execution` / `*Approval` **活指针**，而 `run()` 在后台 goroutine 里持续改这些对象。互斥锁只护住了「写」，对已经逃逸出去的读者完全无效——这是设计上就没锁住，不是漏了一行。

  生产后果比测试报错严重：
  1. handler 把 `Execution` 交给 `encoding/json` 时，编码器要遍历 `NodeStates` 这个 map。若此刻引擎正在写它，Go 运行时抛 **`fatal error: concurrent map read and map write`**——这是 runtime throw，`recover()` 拦不住，整个 `workflow-svc` 进程直接消失。
  2. 读 `Status` / `ErrorMessage` 这类 string 字段是读「指针 + 长度」两个字，撕裂读可能拿到非法指针。
