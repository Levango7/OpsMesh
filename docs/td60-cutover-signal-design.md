# TD-60 切流信号化设计（D+C 的前置问题）

> **缘起**：并行线 TD-90 收尾时在提案 §4 记录决策「近期 D + C」，同时留下一个派生问题：
> 「分批切换的**批次选择如何被信号化**——登录/注册请求没有 JWT，服务端无从判断请求属于哪一批租户，
> 需要请求侧带租户标识或客户端按批次切面。这一点定下来之前我不做按租户路由实现。」
> 本文回答该问题。**结论先说：以「用户名」为信号是对的，「以租户为信号」在当前 schema 下不可实现。**
>
> **基准**：`318eaff`（2026-10-10）。文中 `file:line` 均可在该基准复现；全部结论基于实测而非推断。

---

## 1. 先修正一个前提：租户不能做路由键

「按租户分批」在字面上不可实现，有三条实测依据：

| # | 事实 | 证据 | 推论 |
|---|---|---|---|
| 1 | 两侧登录都按**用户名**定位用户，租户不参与查找 | 控制面 `auth_login.go:171` `s.store.GetUserByUsername(body.Username)`；auth-svc `internal/service/service.go` `Login()` 同样 `GetUserByUsername(req.Username)` | 路由键必须是用户名；租户至多是用户的**属性**，不是查找键 |
| 2 | **auth-svc 的 `users` 表没有 `tenant_id`** | `services/auth-svc/internal/store/schema.sql:3-13`——五张表中仅 `refresh_tokens`（`:47`）带 `tenant_id` | 即便客户端声明租户，auth-svc 侧也无法据其定位或校验用户 ⇒ 租户路由在 auth-svc 侧**无落地面** |
| 3 | 控制面的租户是用户属性，且登录不做租户收敛 | `auth_login.go:171` 无租户条件；租户仅用于审计（`:202` `tenantOrDefault(u.TenantID)`） | 「声明租户 B 就能登 B 的账号」在本仓不成立——账号是全局用户名唯一，租户是标签 |

**⇒ 「按租户分批切换」要么先给 auth-svc 的 users 加 `tenant_id` 并打通租户上下文（schema + 双端改造，属方向 A 的前置），要么改用「按用户群分批」。** 后者零 schema 改动，且与既有实现同构，本文按后者设计（这也正是并行线措辞里「/用户群」那一支）。

---

## 2. 信号其实一直存在，只是不在 JWT 里

并行线的判断「登录/注册请求没有 JWT ⇒ 无从判断」对**租户**成立，对**批次**不成立。四个端点的可用信号：

| 端点 | 凭证形态 | **可用的批次信号** | 备注 |
|---|---|---|---|
| `POST /auth/login` | 无 | **请求体里的 `username`** | 登录本就是「用用户名找账号」，信号天然在场 |
| `POST /auth/register` | 无 | 无（新账号尚无归属） | 见 §4：注册**不该**按请求路由，它是「哪一侧持有新账号」的全局决策 |
| `POST /auth/refresh` | rt Cookie | **JWT `sub`**（解码即得用户 ID） | 两侧同 HMAC 密钥 ⇒ 控制面可解出 auth-svc 签发的 token 的 sub（双轨冒烟已实证） |
| `GET /auth/me` | at Cookie | **JWT `sub`** | 同上 |
| `POST /auth/logout` | at/rt Cookie | JWT `sub` / rt 归属侧 | 登出须在**签发侧**吊销（jti 黑名单 + rt 删除在本进程内），故路由是刚需 |

**⇒ 「无 JWT 就无法路由」这个障碍不存在：用户名与 JWT sub 都是请求内生的、认证前就可读取的标识。** 真正需要设计的不是「怎么拿到信号」，而是「拿到之后按什么规则裁决，以及裁决错了怎么办」。

---

## 3. 裁决规则：显式名册，不做盲目双读

候选规则有三，逐条评估：

| 规则 | 做法 | 判定 |
|---|---|---|
| **R1 盲目双读兜底** | 先问本侧，查不到再问对侧 | ❌ **不安全**：两侧都 seed 了 `admin`/`user-admin`（冒烟已实证同名并存），若 `alice` 在两侧各有一个账号，一次口令提交会被**两个不同账号**校验——口令对了任意一个即登录成功，构成跨库凭证混淆 |
| **R2 显式名册** | 服务端维护「已迁移用户名」集合（或等价确定性规则），裁决前查表 | ✅ 推荐。名册是**人工/受控写入**的，写入前可强制执行唯一性前置（见 §5），从根上排除 R1 的混淆 |
| **R3 百分比哈希** | `sha256(username) % 100 < pct` 决定归侧 | ⚠️ 可作 R2 的**批量装载机制**（一次性把 N% 用户灌进名册），但不宜作实时判据——它让「同一用户在窗口期内换侧」变得静默且不可审计 |

**采用 R2**，名册条目 = 用户名（与查找键一致），并提供两种装载方式：
- **手工/脚本装载**：按运维批次显式追加，附操作审计；
- **哈希批量预生成**：用 `sha256(username) % 100 < N` 生成初始名册快照（人可读、可 diff、可回滚），**快照落地后即固定**，不再实时计算。

## 4. 分端点裁决（路由器放哪）

把裁决放在**控制面 auth handler 内**，而不是通用代理层：

- 通用代理是「鉴权 → 转发」的无状态管道，要在其中按请求体字段裁决，必须缓存/重放 body，且会把路由策略泄漏到所有域；
- auth handler 本就持有语义（它在读 username、在签 token），路由判据与之同层最自然，也便于按端点差异化（见下表）。

| 端点 | 裁决输入 | 归侧判据 | 说明 |
|---|---|---|---|
| `login` | body.username | 名册命中 ⇒ 转 auth-svc；否则本地 | 转出时**必须整请求转发**（含限流状态、审计），不能「本地验完再转」 |
| `me` / `logout` | at 的 `sub` | 名册命中（或 rt 归属侧）⇒ 转 auth-svc | 登出必须在签发侧吊销 |
| `refresh` | rt | 按 rt 归属侧（或 sub 查名册） | rt 是签发侧私有时刻，归属侧唯一正确 |
| `register` | — | **不做请求级路由** | 注册决定「新账号归哪侧持有」，是全局开关（见下），逐请求路由会让同一批次新用户散落两侧 |

**注册的全局决策**：`/auth/register` 与 `/api/v1/users` 建号走哪一侧，由开关
`AUTH_SVC_OWNS_NEW_ACCOUNTS`（默认 false = 控制面持有）表达，与名册正交。
名册管**存量**，该开关管**增量**——两者同时打开才意味着「这一批彻底切完」。

---

## 5. 名册写入的唯一性前置（R1 风险的正面封堵）

名册写入前必须校验，否则会把 R1 的跨库混淆**固化**进路由表：

1. **对侧不存在同名账号**：把 `alice` 写入名册前，先查 auth-svc 侧无 `alice`（或反之）。
   两侧都 seed `admin` ⇒ **`admin` 永远不进名册**，或先做账号合并/改名。
2. **本侧确有该账号**：名册只描述「已确认存在于对侧」的用户，避免把拼写错误固化成「该用户莫名无法登录」。
3. **口令哈希不迁移**：名册切换意味着「从现在起由对侧持有凭证」。若对侧尚无该用户，切换前需先做账号迁移（建号 + 置随机口令 + 首登强制改密），否则已迁移用户将被锁死。
4. 写入须留审计（谁、何时、把哪些用户名写入），并支持一键摘除（回滚粒度 = 名册条目，不是全局开关）。

**⇒ 名册不是「路由表」，是「迁移工单的机器可读形态」**：每一条背后都应对应一次已完成的账号迁移。

## 6. 落地形态（建议，均不触碰并行线文件）

1. **配置面**：`AUTH_SVC_PROXY_ENABLED`（现全局开关）保持「整域开关」语义不变，作为 D 的执行件；
   新增 `AUTH_CUTOVER_ROSTER`（名册来源：文件路径或内联清单）与 `AUTH_SVC_OWNS_NEW_ACCOUNTS`。
   部署旋钮面按既有惯例补进 `deploy/docker/docker-compose.prod.yml` 与 `deploy.sh` 的 `.env` 模板（本线已为 auth-svc 建过同样的五个旋钮，可直接照式补）。
2. **裁决点**：控制面 `/api/v1/auth/login`、`/auth/me`、`auth/refresh`、`auth/logout` 四个 handler 内
   各加一处「名册命中 ⇒ 转 auth-svc」分支；转发复用既有 `svcproxy` 的 auth 域规则
   （`ForwardCookie` 已打通凭证投递，无需新造通道）。
3. **观测**：每次命中名册记一条结构化日志（`user`、`from`、`to`），便于回答
   「这个用户为什么被送去 auth-svc」；名册条目数作为指标暴露，便于判断切流进度。
4. **回滚**：摘除名册条目即单用户回退；清空名册 = 回到纯本地；均无需重启
   （名册文件热加载，或变更后一次性 reload）。

## 7. 与既有决策的衔接

- **D（整域开关）**：本文不动它，且它是**第一阶段唯一执行件**——在名册机制就绪前，
  任何「按批切换」都不应打开（开了也不可能正确路由）。
- **C（按用户群分批）**：本文给出其可执行形态：名册 + 唯一性前置 + 分端点裁决。
- **A（同库同表）**：若将来立项，本文的「名册」可退场，但仍需保留 §5 的唯一性
  检查作为迁移期工具；租户化路由（§1 所述的加 `tenant_id`）也应在那时一并做，
  而不是现在半吊子接上。
- **给并行线的交接**：其担心的「机制与真实流程不符」正是 §4 分端点表与 §5 前置
  要解决的问题；本文可作为按用户群路由实现的规格输入。

## 8. 待确认（不属本线单方面决定）

1. 名册的**载体**：文件（可 diff、可审计、需挂载）还是配置中心/数据库表（可在线改、需新增写入面）？倾向文件 + 部署流水线变更。
2. 账号迁移的**执行方**：切换前把用户从控制面搬到 auth-svc，由谁在何时做（运维脚本 / 一次性 job）？这决定名册是人工维护还是系统维护。
3. **已登录会话**的处理：切换发生时，控制面签发的未过期 at 仍可用（名册按 sub 路由，会被送去 auth-svc，而 auth-svc 无该用户 ⇒ 401）。需要决定：是允许「切换即踢下线重登」，还是做 rt 迁移。
4. 前端是否需要感知（如切换后首次 `/me` 401 时引导重登而非报错）。

---

## 9. 结论

**信号不是问题，键是什么才是问题。** 并行线的提问预设了「按租户路由」，但租户在 auth-svc 侧无落脚点；改为「按用户名（存量）/ 全局开关（增量）」后，信号在四个端点上全都现成——登录用请求体用户名，其余三个用 JWT sub。真正的工作量在裁决规则与迁移前置（名册 + 唯一性校验），而非信号获取。

`deploy/docker/docker-compose.prod.yml` 补三个旋钮。机制全默认关闭（空名册 + 总闸 false）⇒ 行为与切流前逐字一致。

### 10.1 §8 四个待确认项的裁定（本方能力范围内的三项）

1. **名册载体**：`AUTH_CUTOVER_ROSTER_FILE`（文件，优先，支持 30s 轮询热更）与
   `AUTH_CUTOVER_ROSTER`（内联，逗号/换行分隔）二选一，**同时给出视为非法配置直接拒绝启动**
   （歧义即 fail-fast，与 `OPSMESH_SERVICE_PROXY` 的"取值非法整体拒绝"同哲学）。文件不存在/内容非法
   ⇒ 启动失败；**运行期重载失败则保留上一份可用名册**（清空会让已迁移用户回落到本地而登录失败，是用户可见事故）。
   格式：一行一个用户名，`#` 起注释；**保留账号 `admin` 装载期即拒绝**（两侧 seed 同名 ⇒ 跨库凭证混淆面）。
2. **账号迁移执行方**：非本方单方面决定，但实现里把能自动化的那半做了——启动/重载时逐条核对
   **本侧是否存在该账号**，不存在即告警（拼写错误？或迁移后已清理）。对侧存在性只有 auth-svc 能答，
   留给 §5 的写入前置在迁移工单侧执行。
3. **已登录会话**：**不主动踢**。裁定依据：`me`/`logout` 按 sub 路由到 auth-svc 后，共享 HMAC 下
   auth-svc 能验签（同价凭证在双轨冒烟里已实证），会话不会瞬时断裂；真正的断点在 **refresh**——
   auth-svc 不认本地签发的 rt ⇒ 该用户在下一次刷新时被强制重登一次。这正是提案 §11.3 写明的语义
   （回退/切换伴随一次强制重登），前端只需把 401 当作"去登录页"（§8.4 属前端线）。
   实现上刻意不做 rt 迁移：迁移会引入"两侧都能续会话"的第二本账。
4. **前端感知**：留给前端线；后端行为已定（切换后 refresh 401 ⇒ 重登，登录被路由到 auth-svc）。

### 10.2 实施中发现并补上的一处设计缺口

- **`change-password` 未在 §2 端点表内**：首登改密的令牌是**不透明串**、只存在于签发侧的会话存储
  （`SessionStore.CreateChangePasswordToken`）；登录被路由到 auth-svc 后该令牌也在 auth-svc 侧。
  若本地 handler 消费失败就返 401，首登用户会被**卡死在改密页**。实现按同一"归属侧"规则补齐：
  本地消费不到 ⇒ 转 auth-svc。
- **`refresh` 的裁决不能只看归属**：本地持有但用户已进名册 ⇒ **仍送对侧**。否则该用户能靠 rt 轮换
  永远留在本地侧，批次"切完了"不成立。实现用**非破坏性窥视**（`GetRefreshToken`）判定归属，
  绝不能先 `consume`（那会旋转掉本地会话，随后才发现该转发就晚了）。
- **`login` 必须整请求转发**：本地 handler 先解析 body 才知道用户名 ⇒ 转发前必须把 body 还原，
  否则发出"有 Content-Length 无 body"的请求、用户拿到 502（实现踩到并已由用例钉住，变异检验判红）。
- **本地闸先于路由**：`--public-register=false` 与 IP 限流在注册路由之前判定——部署方关掉公开注册
  就是全 403，不会绕道 auth-svc。
- **登录防护的等价性（已按转发结果补记，残余写明）**：名册用户的凭证校验发生在 auth-svc 侧，
  本地 `loginguard` 原本看不到其失败 ⇒ 账号锁定对名册用户不生效。现按**转发后的状态码**在本地补记：
  401（凭证错）⇒ 记失败、2xx ⇒ 清计数、403/409 等账号状态类拒绝与本地语义一致地**不记**。
  用例走真实登录路径并自校准阈值（基线来自干净账号），变异检验「去掉补记」判红。
  **残余**：绕过本地面、直接打 auth-svc 的失败仍不可见——那部分只有对侧口径能覆盖（同类残余：
  密码策略强度、限流窗口两侧一致，均属对侧）。
- **`/api/v1/users` 建号口径**：`AUTH_SVC_OWNS_NEW_ACCOUNTS=true`（且总闸开启）时**拒绝本地建号**
  （409 + 指明去向 auth-svc）。设计 §4 说该开关表达「新账号归哪侧持有」——若本地仍能静默建号，
  声明就不成立（账号建在被切走的一侧，用户登录时对侧查无此人）。auth-svc 侧无等价的运维建号 API，
  故这里是"拒绝+指引"而非转发；判据与 `RouteRegister` 同源（`Enabled() && OwnsNewAccounts()`）。
