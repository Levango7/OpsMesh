## 文档说明

### 目的与范围

本文档为 OpsMesh 平台 AI 能力的统一设计视图，覆盖以下 14 类能力的设计目标、算法选型、数据流、配置项、集成方式与实现状态：

1. 异常检测引擎（Phase 1 已实现）
2. 智能告警（降噪、根因推荐、优先级预测、抑制规则自动生成）
3. 根因分析（RCA）
4. 容量预测
5. 智能运维助手（AIOps Copilot）
6. 智能编排
7. 日志智能分析
8. 模型管理
9. 数据管道
10. AI 安全与治理
11. 性能与成本
12. 集成架构
13. 路线图
14. 附录（配置项汇总、API 端点汇总、参考文献）

不在本文档范围：纯规则驱动的告警引擎（`alertengine.Engine`）、CMDB 拓扑采集、部署编排 DAG 引擎本身的设计（详见 `feature-design.md`）。但本文档会描述 AI 能力如何**消费**这些既有能力产出的数据。

### 设计原则

1. **零依赖优先**：所有 AI 能力在 `--store=memory` 模式下须可独立运行，无外部模型服务依赖；模型推理须可在进程内完成（嵌入式模型）或经 gRPC 调用旁路模型服务（可插拔）。
2. **可解释性硬约束**：所有 AI 决策（异常判定、根因推荐、容量预测、剧本生成）须产出**人读解释**与**置信度**，禁止黑盒决策直接触发生产变更。
3. **人在回路**（Human-in-the-loop）：AI 推荐类能力（根因推荐、剧本生成、扩容建议）默认仅产出**建议**，须人工确认后经审批流执行；仅"读类"能力（异常检测、容量预测、日志聚类）允许自动触发告警/标记。
4. **失败兜底**：AI 能力故障（模型不可用、推理超时、数据缺失）须**降级**而非拖垮主流程；异常检测引擎不可用时回退到纯阈值规则引擎。
5. **租户隔离**：所有 AI 模型、训练数据、推理结果按 `X-Tenant-ID` 行级隔离；模型可按租户私有化训练或共享预训练模型。
6. **审计 100% 留痕**：所有 AI 决策（含"未触发"的负样本）经 `AuditEvent` 落 `audit_log` 表，含模型版本、输入特征、输出结果、置信度、耗时。
7. **可插拔算法**：检测器、预测器、推荐器均按 Go interface 编程，按 flag 切换实现（统计方法 / 机器学习 / 深度学习），便于 A/B 测试与渐进式增强。
8. **资源限额**：AI 推理须受 `rlimit` 约束（CPU/内存/时长），单次推理超时由 `context.WithTimeout` 中止，避免拖垮控制面。

## 异常检测引擎

### 设计目标

异常检测引擎（AI-01）是 OpsMesh AI 能力的**第一块基石**，于 Phase 1 落地。其设计目标：

1. **自动学习指标基线**：无需人工配置阈值，引擎从指标流自动学习均值/方差/趋势，适应业务周期性波动。
2. **检测异常模式**：识别突然飙升、突然下跌、渐变漂移三类异常，区分**季节性波动**与**真实异常**。
3. **多指标覆盖**：当前覆盖 `cpu_usage`、`mem_usage`，规划扩展 `disk_usage`、`net_in`、`net_out`、`connection_count`、`request_latency_p99` 等。
4. **多租户隔离**：`AnomalyRule.TenantID` 用于规则过滤，与 `AlertRule.TenantID` 一致语义。
5. **自包含可复用**：`AnomalyEngine` 不依赖外部 store/server，可被控制面或 agent 复用（agent 端可做边缘异常检测，仅上报异常告警减少带宽）。
6. **降级安全**：`--anomaly-detection=false` 时引擎为 nil，评估流程跳过异常检测，回退到纯阈值规则引擎。

### 算法选型

异常检测引擎提供两种检测算法，由 `AnomalyRule.Detector` 字段切换：

#### 3.2.1 BaselineDetector（滑动窗口 + Z-Score）

表：BaselineDetector 算法说明

| 维度 | 说明 |
|------|------|
| 算法 | 维护滑动窗口（默认 100 点），计算均值 μ 与标准差 σ，用 Z-Score 检测异常 |
| 公式 | `IsAnomaly(x) = |x - μ| / σ > threshold`（默认 threshold=3.0 即 3σ，约 99.7% 置信区间） |
| 适用场景 | 稳定基线的偏离检测，如稳态服务的 CPU 使用率 |
| 优点 | 简单可解释、O(1) 增量更新、无超参调优负担 |
| 缺点 | 对突变敏感度低（窗口较大时新值影响被稀释）、不适应非平稳序列 |
| 窗口大小 | 默认 100，由 `--anomaly-window-size` 配置 |
| 标准差计算 | 总体标准差（n 而非 n-1），窗口数据视为完整总体 |
| 边界处理 | 窗口数据少于 2 个或 σ=0 时 `IsAnomaly` 恒返回 false |

#### 3.2.2 EWMADetector（指数加权移动平均 + 方差）

表：EWMADetector 算法说明

| 维度 | 说明 |
|------|------|
| 算法 | 维护 EWMA 与 EWMA 方差，对近期数据加权更高，对突变敏感 |
| 递推公式 | `diff = x - ewma`；`ewma = ewma + α * diff`；`ewmaVar = (1-α) * (ewmaVar + α * diff²)` |
| 异常判定 | `IsAnomaly(x) = |x - ewma| / sqrt(ewmaVar) > threshold` |
| 适用场景 | 突变检测，如流量突然飙升、错误率突然上升 |
| 平滑系数 α | 默认 0.3，越大越敏感（新数据权重高），越小越平滑（历史权重高） |
| 优点 | 对突变敏感、内存占用 O(1)、适应非平稳序列 |
| 缺点 | 对渐进漂移不敏感、α 需调参 |
| 边界处理 | 未初始化或 ewmaVar=0 时 `IsAnomaly` 返回 false |

#### 3.2.3 规划算法（Phase 2+）

表：规划中的异常检测算法

| 算法 | 类型 | 适用场景 | 引入版本 |
|------|------|----------|----------|
| IQR | 统计方法 | 鲁棒异常检测，不受极端值影响 | Phase 2 |
| Isolation Forest | 机器学习 | 高维特征异常检测 | Phase 2 |
| LOF | 机器学习 | 基于密度的局部异常检测 | Phase 3 |
| STL 分解 | 统计方法 | 季节性分解 + 残差异常检测 | Phase 3 |
| Autoencoder | 深度学习 | 高维时序异常检测 | Phase 4 |

### 模型训练

异常检测引擎采用**在线学习**模式，无需离线训练：

表：模型训练策略

| 维度 | 说明 |
|------|------|
| 训练模式 | 在线学习（每条数据点实时更新统计量） |
| 增量更新 | `detector.Add(value)` 增量更新，O(1) 时间复杂度 |
| 冷启动 | 窗口数据少于 2 个时 `IsAnomaly` 恒返回 false，避免冷启动误报 |
| 模型版本 | 当前无显式版本管理，统计量随数据流自然演化 |
| 模型持久化 | 当前无持久化，控制面重启后基线从零学习（规划 Phase 2 引入快照持久化） |
| 概念漂移应对 | 滑动窗口自然淘汰旧数据（FIFO），适应概念漂移；EWMA 通过 α 控制遗忘速率 |

**先判后加**语义：`Evaluate` 先调用 `IsAnomaly`（基于历史基线判断），再调用 `Add`（更新基线）。这一顺序有意为之：

- 异常判定基于历史基线，不被当前值污染
- 避免 EWMA 检测器因 `Add` 拉高 ewma/ewmaVar 而稀释 Z-Score
- `Add` 始终执行（即使异常也更新基线），使持续异常时基线逐渐适应，避免持续告警风暴

### 与 alertengine 的集成方式

异常检测引擎与既有 `alertengine` 的集成遵循"**统一事件、统一链路**"原则：

1. **统一事件类型**：`AnomalyAlert` 经 `evaluateAnomalyForDevice` 转换为 `AlertEvent`，与规则引擎产出的 `AlertEvent` 同构，进入同一告警链。
2. **统一告警链**：异常告警与规则告警合并后，统一经过 `Silencer.IsSilenced` → `Inhibitor.IsInhibited` → `Aggregator.Aggregate` → `notify` 链路处理。
3. **统一标签语义**：异常告警的 `Labels` 包含 `ruleID`/`deviceID`/`severity`/`metric`/`tenantID`，可供 `Inhibitor` 标签匹配（如"CPU 异常告警活跃时抑制 mem 异常告警"）。
4. **统一审计**：异常告警触发、抑制、静默均经 `AuditEvent` 落 `audit_log` 表。
5. **降级安全**：`anomalyEngine` 为 nil 时（`--anomaly-detection=false`），`evaluateAlertsOnce` 跳过异常检测，仅执行规则引擎评估。

代码示例：异常告警转换为 AlertEvent（Go）

```go
// evaluateAnomalyForDevice 对单台设备的指标调用 anomalyEngine.Evaluate。
// 异常时将 AnomalyAlert 转换为 AlertEvent，进入统一告警链。
func (s *Server) evaluateAnomalyForDevice(deviceID string) []*alertengine.AlertEvent {
    metrics := s.store.DeviceMetrics(deviceID)
    if metrics == nil {
        return nil
    }
    metricValues := map[string]float64{
        "cpu_usage": metrics.CPU.Usage,
        "mem_usage": metrics.Memory.Usage,
    }
    var events []*alertengine.AlertEvent
    for metricName, value := range metricValues {
        alert := s.anomalyEngine.Evaluate(metricName, deviceID, value)
        if alert == nil {
            continue
        }
        ev := &alertengine.AlertEvent{
            RuleID:   alert.RuleID,
            TenantID: "default",
            DeviceID: deviceID,
            Severity: alert.Severity,
            Message: fmt.Sprintf("异常检测触发：指标 %s=%.2f 偏离基线（均值=%.2f, 标准差=%.2f, Z-Score=%.2f）",
                alert.MetricName, alert.Value, alert.Mean, alert.StdDev, alert.ZScore),
            Labels: map[string]string{
                "ruleID":   alert.RuleID,
                "deviceID": deviceID,
                "severity": alert.Severity,
                "metric":   alert.MetricName,
                "tenantID": "default",
            },
            FiredAt: alert.Timestamp,
            Values:  map[string]float64{alert.MetricName: alert.Value},
        }
        events = append(events, ev)
    }
    return events
}
```

## 智能告警

### 设计目标

智能告警能力（AI-02 ~ AI-05）旨在解决传统阈值告警的三大痛点：

1. **告警风暴**：一次故障触发数百条告警，淹没根因告警 → AI-02 告警降噪
2. **根因难寻**：运维人员需人工排查告警关联 → AI-03 告警根因推荐
3. **优先级失真**：所有告警同等对待，重要告警被低优先级告警淹没 → AI-04 优先级预测
4. **抑制规则手工配置**：抑制规则需运维经验，配置不当导致漏报或误抑制 → AI-05 抑制规则自动生成

### 告警降噪

#### 4.2.1 当前实现：基于标签的分组聚合

当前 `alertengine.Aggregator` 已实现基于标签的分组聚合（属于规则驱动而非 AI 驱动）：

- 按 `groupBy` 指定的标签字段（如 `deviceID`/`severity`/`ruleID`）对事件分组
- 每组最多保留 `maxGroup` 条（默认 100），避免单次评估产出过多相似告警
- 用途：避免告警淹没通知渠道，按设备/严重度等维度归并展示

#### 4.2.2 规划增强：基于相似度的告警聚合（Phase 2）

表：基于相似度的告警聚合算法

| 维度 | 说明 |
|------|------|
| 输入 | 同一时间窗口内的告警事件列表（含 Message/Labels/Values） |
| 相似度计算 | 文本相似度（Levenshtein/余弦）+ 标签相似度（Jaccard）+ 指标值相似度（欧氏距离） |
| 聚合策略 | DBSCAN 密度聚类，相似度 ≥ 阈值的告警归为同组 |
| 代表选择 | 每组选最早触发 / 严重度最高的告警作为代表，其余作为关联告警 |
| 输出 | `AlertGroup{ Representative, Related[], SimilarityScore }` |
| 配置项 | `--alert-dedup-similarity-threshold`（默认 0.8）、`--alert-dedup-window`（默认 5m） |

#### 4.5.1 设计目标

#### 4.5.2 算法

表：抑制规则自动生成算法

| 步骤 | 算法 | 说明 |

    TriggeredBy        string

    Report             string           // 人读 Markdown 报告

## 容量预测

### 设计目标

容量预测（AI-07）旨在基于历史指标数据**预测未来资源容量需求**，提前预警容量瓶颈并给出扩容建议。预测粒度：

- 短期预测：未来 1~7 天，用于容量预警
- 中期预测：未来 7~30 天，用于扩容规划
- 长期预测：未来 30~90 天，用于预算规划

### 算法

表：容量预测算法对比

| 算法 | 类型 | 优点 | 缺点 | 适用场景 | 引入版本 |
|------|------|------|------|----------|----------|
| 线性回归 | 统计 | 简单可解释、推理快 | 仅适合线性增长 | 稳定增长场景 | Phase 3 |
| ARIMA | 统计 | 适合平稳时序、可解释 | 需差分平稳化、不适应多季节性 | 短期预测 | Phase 3 |
| Prophet | 统计 | 自动处理季节性/节假日、可解释 | 需 Python 依赖、推理较慢 | 中长期预测 | Phase 3 |
| LSTM | 深度学习 | 适合长序列、多变量 | 黑盒、需大量数据、推理慢 | 长期预测 | Phase 4 |
| Hybrid | 混合 | 集成多模型、按场景切换 | 复杂度高 | 全场景 | Phase 4 |

### 预测维度

表：容量预测维度

| 维度 | 指标 | 预测目标 | 预警阈值 |
|------|------|----------|----------|
| CPU | `cpu_usage` | 未来 7 天峰值 | ≥ 80% 持续 1h |
| 内存 | `mem_usage` | 未来 7 天峰值 | ≥ 85% 持续 1h |
| 磁盘 | `disk_usage` | 未来 30 天耗尽时间 | ≥ 90% 或耗尽 ≤ 7 天 |
| 网络 | `net_in`/`net_out` | 未来 7 天峰值 | ≥ 带宽 80% |
| 连接数 | `connection_count` | 未来 7 天峰值 | ≥ 最大连接数 80% |
| 业务指标 | `request_qps`/`active_users` | 未来 7 天峰值 | 由业务 SLO 定义 |

### 与配额系统的联动

容量预测与 `QuotaManager`（P2-B5 多租户资源配额）联动：

- 扩容建议含**目标配额值**，经审批后由 `QuotaManager` 调整配额
- 配额调整触发 `orchestration` 扩容剧本（如 K8s HPA 调整、新设备纳管）

表：容量预测与配额联动

| 扩容建议 | 预测 7 天内资源需求 > 当前配额 | 生成扩容建议（含目标配额） |
| 自动扩容 | 预测置信度 ≥ 0.9 且启用自动扩容 | 经审批后调整配额 + 触发扩容剧本 |

## 日志智能分析

### 设计目标

表：模型生命周期阶段

| 阶段 | 说明 | 触发条件 |
|------|------|----------|
| training | 训练中 | 训练任务启动 |
| validated | 验证通过 | 评估指标达标 |
| deployed | 已部署 | 通过 A/B 测试或人工审批 |
| deprecated | 已弃用 | 性能退化或新版本上线 |
| retired | 已退役 | 不再使用 |

### 模型评估

表：模型评估指标

| 指标 | 公式 | 适用场景 |
|------|------|----------|
| 准确率 (Accuracy) | `(TP + TN) / (TP + TN + FP + FN)` | 分类任务 |
| 召回率 (Recall) | `TP / (TP + FN)` | 异常检测（重视漏报） |
| 精确率 (Precision) | `TP / (TP + FP)` | 异常检测（重视误报） |
| F1 | `2 * P * R / (P + R)` | 综合评价 |
| 误报率 (FPR) | `FP / (FP + TN)` | 异常检测（运维关注） |
| 漏报率 (FNR) | `FN / (FN + TP)` | 异常检测（运维关注） |
| 推理延迟 (Latency) | P50/P95/P99 | 实时性要求 |
| MAPE | `mean(|actual - predicted| / actual)` | 预测任务 |
| RMSE | `sqrt(mean((actual - predicted)²))` | 预测任务 |

### A/B 测试框架

表：A/B 测试框架设计

| 维度 | 说明 |
|------|------|
| 实验设计 | 流量分桶（按 deviceID hash 分桶），对照组用旧模型，实验组用新模型 |
| 评估指标 | 业务指标（MTTR/误报率/用户满意度）+ 模型指标（准确率/延迟） |
| 显著性检验 | t 检验 / Mann-Whitney U 检验，p < 0.05 视为显著 |
| 自动决策 | 实验组显著优于对照组 → 自动晋升；否则 → 保持旧模型 |
| 实验时长 | 默认 7 天，覆盖业务周期 |
| 流量比例 | 默认 10% 流量给实验组 |
